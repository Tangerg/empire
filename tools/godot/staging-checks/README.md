# Native campaign staging checks

Run `bash tools/godot/staging-checks/run.sh`. The default gate uses frozen original rendered expectations and current native schema-3 metadata, not live TypeScript regeneration. It compares 45 views, immutable rows, explicit actor bindings and native portrait/catalog and source scene PNG hashes. The check-only catalog JSON is disposable; the shipped runtime loads native PO.

`CampaignStaging.Create(presentationText, portraitCatalog, state, battleNode, level, metadata, hasPendingRequest)` returns an immutable view. The explicit `CampaignStagingText` supplies the shared `GameText` service and identity/content names; it localizes campaign/chapter titles, shell action/accessibility labels, staging headings and action notes, HP/rank/disposition messages, and explicitly mapped resource/relation names. The chapter table is their single owner; levels contain chapter IDs, not repeated chapter titles. The root still owns canonical request/start/reentry/outcome transitions.

Built-in unit and level names/descriptions still come from the canonical content boundary and await that content migration. This suite does not claim full game internationalization. Genuine user-authored names remain literal data; built-in content names will be resolved at their presentation boundary rather than stored as translated core facts.

`CampaignStagingScreen.ShowStaging(view, assets, startBattle, exitCampaign)` renders those facts inside the shared shell. Start and Exit are mutually exclusive per binding. Stale, double, detached, unmounted and remounted callbacks cannot navigate without an explicit new binding. Reentry still means restart from the same pending request, not resume.

Native source documents own presentation metadata. `export-grayflag.ts` no longer writes them; it copies declared, hash-verified scene artwork and verifies native portrait catalog bytes without overwriting them. The shared schema has exactly `schema`, `titleKey`, `completionLabelKey`, `menu`, `menuArt`, `chapters`, `storyScenes`, `battleTotal`, `joinAfter`, `relationLabelKeys`, `resourceLabelKeys`, `portraits` and `levels`. `validate_narrative.py` rejects missing/extra fields and obsolete duplicated chapter labels. Portrait values are catalog IDs, never embedded source/path/hash records. There is no earlier-schema fallback.

The frozen oracle still checks original roster filtering, HP rounding, resource ordering, first-five nonzero relations, signs/bars, actor bindings and artwork. Disposition expectations intentionally use localized messages instead of exposing domain codes. Synthetic resource/relation IDs in one fixture have explicit test-only catalog messages and metadata mappings; production never falls back to displaying unknown IDs. Native tests separately clone schema-3 metadata with unavailable art to check diagnostics and real unit-sprite fallback, then run all 45 cases against actual exported art. Precise missing-art diagnostics remain available through `RenderingDiagnostics`; widgets show one localized, player-safe failure message instead of source/resource paths.

Named campaign roster rows resolve the shared story-schema-3 `identityNameKeys` by campaign unit ID, never by unit class. The frozen historical oracle stays unchanged: the check explicitly replaces only Torren/Elin class-label expectations with personal names and retains every other field. Focused guards cover shared-class identities, reordered/fallen members, all declared roster names, missing identities/keys, injected locale, unchanged dialogue and generic class labels, and projection state/digest preservation.

The metadata comparison resolves all seven narrative portrait IDs through the shared native catalog under `godot/assets/runtime/narrative-static`. The frozen oracle stays untouched; the pure metadata check verifies ID bindings and native source derivation against its original portrait filenames. Scene and level metadata keep their existing source/export checks. Catalog hashes validate native portrait bytes, including the Mirelle candidate pending in-scene visual acceptance, without comparing them to obsolete original cards. These source changes still require the current verification gate; previous passing checkpoints do not establish acceptance.
