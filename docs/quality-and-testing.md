# 验证 SRPG 引擎改动

本页说明当前测试层次、常用命令和合并前验收门槛。测试必须验证领域不变量和跨层契约，不能只检查页面能否渲染。

> 文档类型：How-to · 状态：整仓类型、规则、应用、架构和性能测试已配置 · 测试运行器：Vitest

## 运行标准检查

从仓库根目录运行完整检查：

```bash
npm run typecheck
npm test
npm run build
```

三条命令分别验证：

- TypeScript 工作区类型和跨包导入
- 整仓 Vitest 测试
- 类型检查后构建四个应用

`npm run build` 已包含 `npm run typecheck`。本地开发时可以先分别运行，以便更快定位错误。

## 按范围运行测试

修改单个包时先运行对应测试，再运行整仓测试：

```bash
npx vitest run packages/battle-engine
npx vitest run packages/campaign-engine
npx vitest run packages/editor
npx vitest run packages/game-ui
npx vitest run packages/experience-lab
```

使用监听模式：

```bash
npm run test:watch
```

构建单文件体验包：

```bash
npm run build:experience
```

产物位于 `dist/experience-lab/index.html`。构建成功只证明资源可以打包，仍需通过 `file://` 打开并人工完成关键流程。

## 战斗规则测试

规则测试应覆盖合法、非法和边界三类输入。每个新机制至少验证：

1. 合法 Action 修改正确状态
2. 非法 Action 抛出 `IllegalActionError` 或领域错误
3. 失败后状态与提交前完全一致
4. 预测与正式结算一致
5. 事件顺序与状态变化一致
6. 克隆后的 AI 模拟不污染原状态
7. 多引擎实例不会共享可变注册表

伤害机制还应断言 `DamageBreakdown.modifiers`，不能只断言最终数字。这样可以发现乘区顺序、来源缺失和减伤封顶错误。

## 扩展契约测试

开放类型只完成 declaration merging 不算实现。扩展测试应从装配到消费跑完整链路。

### Action 或能力

验证以下链路：

```text
类型 → 注册 → 合法性 → 执行 → Event → AI 估值 → 实例隔离
```

自定义能力缺少 AI evaluator 时，测试应明确失败或证明 AI 不会枚举该能力。不能接受静默基础分。

### 目标

目标测试需要验证：

- 描述和进度
- `pending`、`success`、`failure`
- 激活、隐藏、完成、失败和取消
- 子目标刷新顺序
- AI objective advisor
- 与场景效果的交互

### 场景条件和效果

场景测试需要验证：

- 条件只读取权威状态
- 效果只修改聚合内事实
- 一次性触发器只触发一次
- 循环触发器遵守 occurrence、起止回合和最大次数
- 新事件进入 `eventCounts`
- 失败的效果回滚整个 Action

## 关卡测试

每张生产关卡至少运行三种测试。

### 格式与引用

调用 `validateLevel(rules, level)` 并要求没有 error——它一次问完两件事：文档对着内容目录自不自洽，以及这套规则集有没有实现文档点名的每条规则。再通过 `mapFromLevel()` 与 `terrainRows()` 做地形往返。

「已发布关卡零错误」是一条永远为真的断言看起来的样子：它不能证明一张**坏**关卡会被拒。`level-lint.test.ts` 是反向语料——每份关卡只种一处毛病，断言恰好报一条错，并且这条错要点出出问题的那个名字。它先写在旧实现上跑通，再作为重构的围栏。

### AI 冒烟

让 AI 驱动双方运行固定回合数，断言：

- 每个 Action 合法
- 每个 AI 回合最终到达 `endTurn`
- 状态没有非法重叠或悬空引用
- 场景触发器没有无限循环

AI 冒烟不能代替平衡测试。它只能证明关卡可推进。

### 数值与目标

为关卡声明的设计承诺添加断言，例如：

- 关键单位不会被首回合必杀
- 增援坐标可用且 key 唯一
- 目标区域可达
- 保护目标存在并被正确引用
- 推荐回合内至少存在一条获胜路径
- 资源足以使用教学要求的能力

题材包可以增加自动审计函数，但审计必须复用引擎查询和预测。

## 编辑器测试

编辑器采用领域与 DOM 两层测试。

`EditorDocument` 测试验证：

- 地形、归属、单位、海拔、悬崖和掩体修改
- 地图缩放与裁剪
- 序列化和反序列化
- `toLevel()` 往返
- 不变量错误

`EditorApp` 测试在 jsdom 中验证：

- 工具按钮和笔刷手势
- 撤销与重做
- 自动草稿
- 玩家和规则表单
- 导入与导出数据
- 错误单位染色和检查面板

新增高级字段时，必须先加入往返测试。没有往返测试的字段不应出现在可视化表单中。

## 表现测试

表现测试优先验证结构和契约，不依赖像素级截图。

当前关键断言包括：

- `SceneViewport` 的 inset 和指针映射
- 道路、地面、单位和前景的 DOM 顺序
- `ArtProvider` 与 `BattlePresentation` 回退
- 栅格图集裁剪坐标
- 帧条元数据校验
- 共享 RAF 循环在空闲时停止
- 减少动态效果模式停在稳定帧
- 视图销毁时注销动画

人工视觉检查仍然必要。结构测试无法发现色彩、比例、透明边缘和场景构图问题。

## 架构测试

`architecture-boundaries.test.ts` 扫描源码导入。它应保持少量稳定规则，不应为每次违规增加例外。

修改包结构后至少确认：

- 核心生产依赖图无环
- 战斗内核不导入内容和表现
- 内容包不导入表现
- 引擎与内容不使用 DOM
- 编辑器文档不依赖渲染
- 游戏控制器不绕过 `TacticalSpace`
- 默认内容不在核心包导入时隐式注册
- 每条规则只有一个归属：伤害结算、单位回场、一次攻击的落地、这一格能不能站人、谁可以持有资源、一条常驻命令怎么读、一张地图的空间层谁能写、一个触发器什么时候该响、两格之间有多远、一次打击覆盖哪些格
- 每个 `XxxRules` 端口只声明本模块自己读的字段；交给协作者的服务用 `extends` 拿，不抄字段
- 实体字段只由实体自己写：规则模块不出现 `unit.hp = …`、`unit.done = …` 这类赋值
- 引擎里每一次抛出都说明白谁错了：不出现 `throw new Error(`
- 文档表格里点名的每个符号都真的存在（表格是对当下的断言，正文才可以讲被删掉的东西）

如果测试失败，先调整依赖归属。只有测试规则与真实边界不一致时才修改测试。

**属性巡检补单元测试补不到的那一半。** 单元测试说「这条规则做什么」，`invariant-sweep.test.ts` 说「任何一份状态都不许长成什么样」：一格站两个单位、乘员挂在已消失的载具上、账户为负、已阵亡者仍在咏唱、事件指向从未存在的单位。它跑十六章 × 三档 AI，每条指令后检查一次（约 1.4 万份状态、4.4 万条事件），顺带抽查存档往返与撤销重演。两条臂都用手工植入缺陷验证过，覆盖计数本身也被断言——否则一个悄悄不再覆盖任何东西的巡检会静默通过。

**加一条守卫，就先破坏一次。** 归属类守卫是靠正则扫源码的，一条永远为真的正则和一条正确的正则看起来一模一样。把被禁的写法手工写回去一次，确认它真的红了，再改回来——每一轮的新守卫都这么验过。当前共 46 条。

**破坏一次还不够，要把每一种写法都破坏一遍。** 上一轮的「不许用 `!` 断言」守卫只匹配 `x!.field` 和 `x![i]`——而我恰好也只用这个形状验了它。同一批文件里躺着十六个 `f()!`、`id!`、`g(x!)`，守卫一路绿灯。现在它针对断言运算符本身，四种形状逐一破坏验证过。

**守卫的作用范围本身就是一条断言。** 调用形状守卫原来只看「会 emit 的函数」，注释里写着「纯查询不管」——那条豁免恰好盖住了它本该消灭的东西：十五个查询仍是旧的 `(subject, content)` 形状，另有五个函数把两三个服务当成独立参数传。范围缩小得越顺理成章，越要问它盖住了什么。

**守卫的匹配式只覆盖了「产生值」的一种写法。** 「未绑定的 catch 不许产生值」原来只在 catch 体里搜 `return`——而赋值、副作用、抛一个新错误都是产生值。它漏掉了 AI 循环里的 `catch { events = tryDispatch(endTurn) }`（把规则层任何缺陷变成一次无声的过回合）和关卡存储里的 `catch { existing = [] }`（紧接着把空列表写了回去）。现在守卫按公理的字面执行：未绑定的 catch 体必须为空，并用注释说明为什么；其余一切都要绑定并查看那个错误。

**守卫按名字匹配，就只挡得住名字。** 「每个扩展点都建在共用注册表上」原来匹配 `export class \w*Registry`——而编辑器的工具集叫 `EditorToolbox`，一个手写 `Map` 加一个 `get`，其余一概没有；而且守卫只扫引擎。现在它按形状匹配：一个类自己持有键值表、又声明了 `register`/`define` 往里写，就必须建在基类上。两条豁免各有理由（版本阶梯、动画调度器），而不是「它不叫 Registry」。

**文档也可以被守卫。** 能力目录承诺「每条规则的归属都写在这里」，而五行点名的注册表早就加上了 `Default` 前缀——照着表去 grep `AiIntents`、`ResourceSubjectResolvers` 的读者什么都找不到。守卫只扫**表格行**：表格是对当下的断言，正文则必须能讲「这个名字被改成了什么、那个被删了」。范围一旦分对，这条守卫就既挡得住文档腐烂，又不妨碍文档讲历史。

**「没有第三种答案」也是一种漏判。** 本轮的错误分类守卫把引擎里八十四处裸 `throw new Error` 逼出来重新归类，多数确实是「调用方错了」。但其中一处两者都不是：增援落到有人站着的格子上——那是普通对局。它此前以裸 `Error` 抛出，穿过外壳唯一那道 `instanceof IllegalActionError` 判断，直接把战斗打断。分类的价值不在于换个类名，而在于逼你对每一处回答「这到底是谁的错」——答不上来的那一处，往往才是真正的缺陷。

**行首锚点会把「问句」放走。** 本轮的实体守卫第一版写成 `^\s*…\.field\s*=`，一次抓到八个模块。把锚点去掉、再把 `+=` 也算进去之后，又掉出两处：`if (commander) commander.owner = …` 和 `if (leader.commanderId === null) leader.commanderId = …`——两条都是**写在 `if` 后面同一行**的赋值。守卫每多要求一个字符，就多放走一类写法；而放走的这一类恰好是「顺手补一句」的那一类，也就是最可能绕过归属的那一类。

**抄一个字段，就抄了一个问题。** 本轮的端口守卫（每个 `XxxRules` 只许声明本模块自己读的字段）报出十七处（十六处改掉，一处按理由豁免），它们不是十七处样板：五个端口各写了一遍 `GridRules` 的 `grids`，`AiRules` 抄了 `turnOrders` 而 `AiTurnContext` 紧接着把 `activeTurnOrder` 的函数体重写了一遍，`WeaponAreaRules` 声明了自己一次也没读过的 `areaShapes` 而「一次打击覆盖哪些格」在两个模块里各写了一份。字段被抄走，是那条规则没有归属的最早征兆——比重复的表达式更早。

**守卫查的是比较，硬写成数据的 id 它看不见。** 本轮加的「不许拿 ability id 猜这条命令是什么」按 `x.ability === '…'` 两个方向匹配，六处违规当场落网。第七处不是比较：点敌人自动选位后，`commandClick` 把选出来的那条命令按 `'attack'` 这个字面量装进 `TargetSelection`，正则一个字都对不上。抓到它的是行为测试——一套只有内容包自己的「齐射」、没有 `attack` 的规则集，点下去必须把齐射举起来。归属类守卫只能证明「没人在问 id」，证明不了「没人在替 id 做主」；这一半要靠一个不含核心 id 的规则集去跑。

**还要读失败信息本身。** 破坏验证时我两次用 `grep -c FAIL` 判断，而 vitest 把那行写到 stderr，脚本一直读到 0 —— 于是「没抓到」被我读成「抓到了」。现在逐条确认失败信息里真的点出了被破坏的那个符号。

**守卫的扫描范围也是它的一部分。** 题材包此前不在任何守卫的视野里，于是那里藏着一个 `catch { return null }`——「这个包没有这张图标」和「素材解析坏了」被答成同一个 null。把题材包加进扫描范围之后它当场就被点了出来。

新守卫也会抓到自己那一轮的东西：本轮加空间层守卫时，无环守卫立刻报出 `spatial.ts -> state.ts -> domain/map-layers.ts -> spatial.ts`——一个纯几何函数住在耦合了状态的模块里，这才是那条环的根因。

## 性能基准

运行核心 benchmark：

```bash
npm run bench:core
```

遵守测量驱动原则：

1. 先记录可复现的关卡、单位数和运行环境
2. 找到占总耗时主要比例的路径
3. 修改一个瓶颈
4. 同时运行正确性测试和 benchmark
5. 记录中位数、波动和内存影响

不要用一次本地运行的绝对时间设硬门槛。基准更适合比较同一机器上的前后变化。

缓存必须有失效测试。任何为了性能引入的缓存都不能成为第二状态真值。

## 构建验收

`npm run build` 依次构建：

1. 主游戏
2. 编辑器
3. 引擎能力 Demo
4. 超级体验关卡

构建后检查：

- 每个 `dist/*/index.html` 存在
- 主游戏和编辑器通过 HTTP 预览可打开
- 单文件体验包通过 `file://` 可打开
- 图片、CSS 和字体没有外部相对路径遗漏
- 浏览器控制台没有模块、跨域或素材 404 错误
- 页面销毁后没有残留浏览器自动化进程

## 当前工程缺口

仓库当前没有 GitHub Actions 工作流，因此远端不会自动运行上述检查。推送前必须在本地执行完整检查。

下一步工程化优先级应是：

1. 建立类型、测试和构建 CI
2. 为单文件体验包增加发布产物检查
3. 建立种子玩家匿名体验指标和版本标识
4. 为复杂关卡增加确定性 Action 冒烟与性能预算
5. 为技术文档增加相对链接检查
