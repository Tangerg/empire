# 设计可读、可组合的 SRPG 战斗

本页定义当前战斗系统的体验目标、机制结构、结算语义和数值护栏。它指导关卡与内容设计，不重复代码架构，也不描述任何具体剧本。

> 文档类型：Conceptual · 状态：核心循环和高级战术原语已实现 · 代码真值：`packages/battle-engine/src/` · 逐项状态：[引擎能力目录](./engine-capabilities.md)

## 战斗体验目标

一场战斗应让玩家持续完成三类判断：读懂局势、组织协同、承担选择后果。复杂度来自机制之间的组合，不来自隐藏概率和例外规则。

系统追求以下体验：

- **可读**：界面能在提交前解释落点、目标、伤害、反击和资源消耗
- **可控**：相同状态和 Action 产生相同结果，失败可以复盘
- **有空间感**：高地、悬崖、视线、朝向、掩体和隘口改变最优解
- **有组织感**：单位通过援护、指挥、阵形、士气和任务目标形成队伍
- **有节奏**：推进、占领、攻城、增援和阶段目标推动战线变化
- **有身份**：兵种、武器、职业和资源形成职责，不靠大量专属分支

## 复杂度预算

引擎取经典战略角色扮演游戏（SRPG）机制的并集，单场关卡只选择其中一部分。内容设计不能把所有能力同时打开。

一张常规关卡建议控制在以下预算：

| 维度 | 建议预算 | 原因 |
| --- | --- | --- |
| 主目标 | 1 个组合目标或 1 至 2 个并列目标 | 保持胜利路径清楚 |
| 额外目标 | 0 至 2 个 | 提供风险收益，不干扰主线 |
| 主导空间规则 | 2 至 3 个 | 例如高地、桥梁、方向掩体 |
| 新机制 | 1 个 | 给玩家建立学习和验证窗口 |
| 关键资源 | 1 至 2 种 | 限制同时管理的账户数量 |
| 指挥体系 | 0 至 2 个 | 避免光环与战术按钮淹没单位职责 |
| 动态阶段 | 1 至 3 次 | 每次都要改变局势，而不是只增兵 |

超级体验关卡可以突破常规预算，但它承担验证任务，不代表量产关卡模板。

## 核心战斗循环

玩家回合围绕“选择单位、选择落点、选择行动、确认结果”展开。菜单、AI 和正式结算共用同一套合法性与预测服务。

```mermaid
flowchart LR
  Read["读取威胁、目标和资源"] --> Unit["选择单位"]
  Unit --> Move["选择合法落点"]
  Move --> Command["选择武器、能力或姿态"]
  Command --> Preview["查看 CombatPlan"]
  Preview --> Commit["提交 Action"]
  Commit --> Events["生成语义事件"]
  Events --> State["刷新目标、场景和胜负"]
  State --> Read
```

战斗采用阵营轮流行动。单位通常每回合行动一次，部分姿态和编制动作不消耗主行动。`endTurn` 推进状态、资源、冷却、状态、场景触发器、目标和胜负。

## 空间决策

规则地图使用四方向隐藏离散格。表现层可以绘制自然道路和不规则场景，但不能改变合法站位和距离定义。

### 移动与占位

移动场使用按进入成本计算的 Dijkstra：

- 地形按移动类型定义进入成本
- 覆盖层可以增加成本或封锁移动类型
- 上坡与下落受海拔规则约束
- 显式悬崖边可以禁止跨越
- 结构可以阻挡移动
- 敌军按规则阻挡路径
- 友军可以允许穿过，但不能重叠停留
- 飞行和水军由移动配置决定通行能力

移动预览返回最低成本路径。Action 提交时会重新验证完整路径，界面不能自行放宽规则。

### 海拔与视线

海拔是每格独立的整数层，不是地形名称的派生值。地形、覆盖层和结构分别贡献阻挡高度。

直射武器沿离散射线比较以下高度：

1. 射手眼高
2. 目标眼高
3. 中间格的海拔与阻挡顶部

弧射和无需视线的武器使用各自数据策略。攻击者高于目标且达到阈值时获得高地倍率，并把目标掩体降低一级。

### 朝向、侧击与夹击

单位具有北、东、南、西四种朝向。近战根据攻击方向计算正面、侧面和背面：

- 侧击应用 `sideAttackMultiplier`
- 背刺应用 `backAttackMultiplier`
- 对向友军构成夹击时叠加 `flankAttackMultiplier`
- 单位可以通过正式 `face` Action 调整朝向

方位只作用于满足近战条件的武器，远程攻击不会因为屏幕方向偶然触发背刺。

### 掩体与结构

掩体分为半掩体和全掩体，来源包括基础地形、结构和方向边。远程攻击从来袭方向选取更强的保护。

以下攻击会绕开普通掩体：

- 相邻攻击
- 弧射武器
- 带 `ignores-cover` 标签的武器

总减伤在统一管线末端封顶为 60%。高地会把全掩体降为半掩体，把半掩体降为无掩体。

## 伤害和交战

伤害确定且可解释。`CombatModifierPipeline` 收集有序修正，`DamageBreakdown` 把每个来源返回给界面、日志、AI 和平衡工具。

### 伤害管线

默认单位伤害按以下阶段结算：

1. 读取武器威力
2. 应用伤害类型与护甲克制
3. 应用武器对目标标签的专属加成
4. 按攻击者剩余生命缩放到 `0.5 + 0.5 × HP%`
5. 应用军衔、状态、指挥光环和阵形攻击修正
6. 应用高地、侧击、背刺和夹击
7. 累加地形、单位、状态、指挥、阵形和掩体减伤
8. 把总减伤限制在 `0` 到 `0.6`
9. 应用反应等最终倍率
10. 四舍五入并保证存活目标至少受到 1 点伤害

这不是一个写死公式。每个修正由带优先级的 `CombatModifierProvider` 提供，替换或扩展提供者不会改变提交边界。

### 武器和范围

一个兵种可以携带多种武器。武器数据定义：

- 威力、伤害类型和目标标签加成
- 最小射程、最大射程和移动后攻击
- `none`、`direct`、`arc` 三种视线策略
- `single`、`cross1`、`line`、`ring1` 四种范围模板，其中 `ring1` 覆盖中心周围的 3×3 区域
- 是否反击、冷却和资源条件
- 武器级资源，例如弹药
- 命中后状态或强制位移

单位从当前状态中选择合法武器。系统不会在请求武器不可用时静默切回首武器。

### CombatPlan

`CombatPlan` 是一次攻击的不可变计划，包含主目标、范围格、单位命中、结构命中、援护和每个目标的预测结果。界面和 AI 读取计划，执行阶段提交同一计划语义。

范围攻击默认只命中敌对单位与敌对结构，不造成友军伤害。改变该策略需要正式扩展，不能由某个界面临时决定。

### 反击和援护

反击只在以下条件全部满足时发生：

- 规则允许反击
- 防守者在主攻击后存活
- 防守者拥有可反击且可用的武器
- 该武器能覆盖攻击者落点
- 资源和冷却允许使用

防守者从合法武器中选择预计伤害最高者。AI 在保守策略下会避免浪费有限弹药或冷却武器。

反应姿态形成两类邻接协同：

- `guard`：单位承受一次降低后的伤害，放弃该次反击
- `support`：邻接友军可以代替目标承伤，或在主交战后追加援护攻击

每个反应在当前轮次最多触发一次，预测会显示真正受伤者和援护结果。

### 强制位移

推、拉、传送共用一个权威解释器。系统逐格检查边界、悬崖、结构和单位阻挡；提前碰撞可以造成额外伤害和死亡。

武器命中效果和场景效果都调用同一服务，因此 UI、AI、剧情触发和正式结算不会出现不同解释。

## 单位组织与成长

单位保持明确实体身份。状态、资源、朝向、反应、士气、职业和历史都归属于同一 `Unit`，系统不采用实体组件系统（ECS）。

### 状态

状态定义包含叠加策略、持续时间、攻击与防御修正、移动修正、占领限制、周期效果和能力标签封锁。默认生命周期在单位所属方回合开始时推进。

状态的正式数据进入 `statuses` 目录，状态行为进入 `StatusBehaviorRegistry`。`Unit.meta` 只保存不影响核心规则的扩展信息。

### 指挥官与战术

指挥官通过稳定 ID 连接普通单位。链接单位只有在半径内且指挥官存活时获得光环。

指挥体系支持：

- 攻击、防御和移动光环
- 回合资源供给
- 数据定义的范围战术
- 指挥官阵亡后的光环移除、状态冲击和士气损失

战术消耗玩家账户上的资源，并产生正式事件。每个指挥官的战术使用在所属方回合刷新。

### 士气、溃退与投降

士气可以按关卡开关。伤害、友军阵亡和指挥官阵亡会改变士气；达到阈值后，单位可以转化为溃退或投降 marker。

marker 保存完整单位快照，可以被场景效果恢复、复活或移除。跨关名单由战役桥解释 marker，不由战斗核心决定永久死亡。

### 阵形与运输

阵形是数据定义的攻防与移动配置。只有满足邻接友军数量时生效，避免单位脱离队伍后仍保留编队加成。

运输单位保留乘员完整身份。登载和卸载是正式 Action，载具损失会按聚合不变量处理乘员并发出语义事件。

### 当关成长与职业

军衔有新兵、老兵、精英三档。伤害和击败目标产生当关进度，军衔进入伤害修正管线。

职业树由数据定义前置职业、军衔、熟练度、花费和掌握能力。转职保留单位 ID、生命、状态、资源和战斗历史；职业只替换战斗配置与当前职业状态。

英雄气势也是普通单位资源账户。招牌武器通过资源门槛和消耗表达，不需要英雄专用 Action 分支。

## 经济、占领与生产

玩家、单位和武器都可以拥有资源账户。资源适配器决定账户位置、容量、整数规则和 AI 估值。

内置账户包括：

- `funds`：玩家资金
- `command_points`：玩家指挥点
- `momentum`：单位气势
- `weapon_uses`：武器弹药或使用次数

资源事务先按主体和资源合并，再原子校验和扣除。预测不会消耗资源，只有合法提交才扣除。

占领支持两种规则：

- `instant`：合格单位踏入后立即占领
- `progressive`：按单位生命比例积累占领点

据点可以提供回合资源、治疗和招募列表。生产会检查所有权、资金、单位上限、占位和新兵行动规则。

## 任务和动态战场

关卡目标与场景脚本是两个正交系统：目标回答胜负，场景脚本改变战场事实。两者通过语义状态和事件连接，不读取剧情文本。

### 目标组合

内置目标覆盖：

- 歼灭、攻占总部、控制全部据点、坚守回合
- 消灭指定单位、摧毁结构、瘫痪复合目标
- 保护、护送、占区、分数和互动变量
- `all`、`any`、`sequence` 组合
- `optional` 额外目标
- `failOn` 关键失败条件

目标具有稳定运行时 ID、激活、隐藏、完成、失败和取消状态。场景效果可以公开、激活、完成或取消目标。

### 场景条件

条件可以读取：

- 回合阈值和周期
- 当前玩家
- 变量
- 区域中的单位、单位数量和生命比例
- marker 数量
- 语义事件计数
- 结构、复合目标和目标状态
- 组合逻辑

### 场景效果

效果可以修改：

- 变量、状态、资源、士气、归属和队伍关系
- 增援、召唤、撤退、复活、投降和恢复撤退单位
- 推拉、传送和 AI 指令
- 地形覆盖、基础地形、海拔、悬崖和方向掩体
- 区域交战政策
- 结构生命、修复和复合目标位置
- 目标生命周期和语义信号

触发器支持一次性和有界循环。`everyRounds`、起止回合和最大触发次数限制重复脚本，避免无限触发。

## AI 设计

AI 只提交正式 Action，并复用引擎查询和预测。它不会绕过资源、视线、任务或场景交战政策。

当前 AI 能评估：

- 伤害、击杀、反击风险和资源成本
- 占领、生产、治疗、攻城和指挥战术
- 护送、保护、占区和阶段目标
- 高地、掩体、威胁范围和援护
- 士气、阵形、运输与单位指令
- 已注册能力的专属估值

扩展能力必须提供 `AbilityAiEvaluator`。扩展目标应提供 `AiObjectiveAdvisor`。如果只注册执行器而没有 AI 估值，引擎会在配置或枚举测试中暴露缺口，不能靠能力名称硬编码评分。

## 数值护栏

以下护栏限制乘区爆炸和无解僵局：

- 总减伤上限为 60%
- 生命缩放最低保留 50% 输出
- 军衔攻击每档增加 4%，防御每档增加 2%
- 高地、方位和夹击使用清晰的单项倍率
- 援护攻击使用 60% 最终倍率
- 普通伤害至少为 1
- 有限武器只在提交后扣除
- 状态周期伤害可以声明非致死
- 阵形需要持续满足空间条件
- 强力能力通过资源、冷却、最小射程或不可移动后使用限制

推荐用交换速度而非单次伤害判断平衡：普通同级单位在无克制环境中应有 2 至 4 次有效交战窗口。重甲、Boss 和结构可以更长，但必须提供攻城、破甲、目标绕行或阶段变化。

## 关卡设计检查表

发布一张关卡前确认：

1. 玩家能否在首回合读懂主目标和失败条件？
2. 每个关键兵种是否有至少一个独特职责？
3. 高地、掩体和隘口是否改变路线，而非只增加装饰？
4. 是否存在不需要歼灭全部敌人的推进目标？
5. 动态阶段是否改变位置、资源或目标？
6. 每个强敌是否有可预测的弱点或成本？
7. 增援是否提前给出信息或空间预警？
8. AI 是否能理解关卡使用的自定义能力和目标？
9. 失败是否来自可见决策，而非不可见脚本？
10. 是否用自动推演和人工试玩同时验证数值？

## 明确排除的复杂度

当前方向主动排除以下机制：

- 连续时间或即时制战斗
- 百分比命中、暴击和不可注入随机伤害
- FFT 式 CT 行动条和长施法队列
- 全面装备格、物品背包和锻造经济
- 按组件拆散单位身份的 ECS
- 为每个题材复制一套战斗规则
- 让 UI 独立计算合法性或伤害

这些取舍不是技术限制，而是可读性和制作成本预算。

## 当前仍需验证的问题

以下问题需要通过超级体验关卡和种子玩家数据判断，不能只靠继续加代码解决：

- 一场战斗同时使用多少高级机制仍保持可读
- 隐藏格场景中，合法落点和距离提示是否足够直观
- 九人以上队伍的回合时长是否可接受
- 指挥、阵形、士气和职业是否形成协同，还是变成界面负担
- 目标阶段变化是否让战线自然推进
- AI 回合时长和选择质量是否满足大地图
- 确定性战斗是否需要额外的局外风险来源
